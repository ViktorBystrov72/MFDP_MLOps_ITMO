# Урок 4. Датасет для матчинга экспозиции и сделок (Тюмень)

## 1. Источник и состав данных

Данные берутся из **продакшен-хранилища Neolithic** (PostgreSQL / ClickHouse) и операционных выгрузок команды.

| Сущность | Содержание | Пилот Тюмень (ориентир) |
|----------|------------|-------------------------|
| Сделки | Первичные договоры с привязкой к корпусу; источник — выгрузки **госорганов** | ~87k сделок с 2024 г. с `location_id` |
| Экспозиция | Нормализованные объявления новостроек с площадок (Циан, Domclick, сайты СЗ и др.) | ~276k записей (~26k active) |
| Слабые labels | Результат текущего rule-матчинга (полное/частичное совпадение) | ~31k положительных пар в выборке |

**Важно:** матчинг двухэтапный — сначала сделка относится к корпусу, затем к объявлению. Без корпуса кандидатов из экспозиции нет.

Собранный датасет пар: `artifacts/datasets/tyumen_pairs*.parquet`  
(~186k пар: ~31k positive / ~155k negative; train до 2025-07 / hold-out с 2025-07).

## 2. Базовый EDA (выводы для моделирования)

1. **Дисбаланс классов** сильный (~1:5) — нужны class_weight / PR-AUC, не accuracy.
2. **Площадь и этаж** — ключевые признаки, но с шумом: `area_diff` и `floor_diff` информативны, точное равенство редко.
3. **Номер квартиры** часто пуст в экспозиции (особенно вторичка/риелторы) — нельзя строить только на exact flat_number.
4. **Цена** — вспомогательный признак: относительная разница цен может подтверждать матч, но не должна быть единственным ключом.
5. **Same building** — сильный blocker: почти все полезные кандидаты внутри одного корпуса.
6. Текущий rule-каскад даёт много «частичных» совпадений — как weak labels годится, как prod-качество — нет.

## 3. Оценка качества разметки и как улучшить

Текущие labels = `coincidence_degree` из rule-based сцепки Neolithic.

| Проблема | Риск для ML | Улучшение |
|----------|-------------|-----------|
| Ложные полные/частичные сцепки | шум в positives | ручная выборочная валидация ≥500 пар; очередь «на проверку» |
| Много «Нет совпадений» без проверки | смещение negatives | negatives только из того же корпуса (как в датасете) |
| Нет экспертного gold-set | завышенные метрики | hold-out с ручной переразметкой |

Предложение: гибрид — weak labels для обучения + экспертный hold-out для отчёта Precision/Recall.

## 4. Алгоритм формирования выборки и валидация

### Алгоритм
1. Фильтр: город Тюмень, первичка, договор ≥ 2024-01-01, есть корпус.
2. Positive: пары из сцепки со степенью «Полное» / «Частичное».
3. Negative: до 5 случайных объявлений **того же корпуса**, не совпадающих с positive.
4. Признаки: `area_diff`, `floor_diff`, `same_flat_number`, `same_rooms`, `same_building`, `price_rel_diff`.

### Стратегия валидации
- **Temporal hold-out:** train = договоры до 2025-07-01, hold-out = с 2025-07-01 (имитация прод-внедрения).
- Дополнительно: GroupKFold по `complex_id` / ЖК для оценки обобщения на новые ЖК.
- Метрики: Precision, Recall, F1, PR-AUC; бизнес — Coverage цикла экспозиция→сделка.

## 5. Воспроизведение

На серверах компании (GPU при необходимости для эмбеддингов):

```bash
source venv/bin/activate
export PYTHONPATH=src
# выгрузка CSV из PG (или готовые artifacts/datasets/tyumen_*.csv)
python scripts/build_tyumen_dataset.py
```

Артефакты: `artifacts/datasets/tyumen_pairs_train.parquet`, `tyumen_pairs_holdout.parquet`.
