# MFDP_MLOps_ITMO — Матчинг экспозиции и сделок (Neolithic)

Учебный MLOps-проект для рабочего проекта **Neolithic** (Неолитика) — сервис сопоставления объектов недвижимости 
из **экспозиции** (объявления на продаже) с **сделками** (факт продажи), чтобы отслеживать полный жизненный цикл квартиры или другого объекта недвижимости.

## Контекст предметной области

Проект **Neolithic** собираем для застройщиков данные о том, сколько квартир сейчас в экспозиции (на продаже), 
с агрегацией по множеству площадок. Параллельно накапливаются данные о **сделках** — объектах, которые ушли с рынка как проданные. 
Без надёжного матчинга невозможно:

- связать «исчезнувшее объявление» с конкретной сделкой;
- посчитать реальные сроки продаж;
- отличить продажу от снятия объявления без сделки;
- отследить повторное выставление той же квартиры.

**Задача проекта** — реализовать этот матчинг как воспроизводимый ML-сервис с измеримым качеством и полным MLOps-циклом.

## 1. Бизнес-анализ (Business Understanding)

Этап посвящён формулировке целей проекта, определению заинтересованных сторон и оценке текущей ситуации. Структура 
соответствует методологии CRISP-DM и [жизненному циклу ML-модели](https://neerc.ifmo.ru/wiki/index.php?title=Жизненный_цикл_модели_машинного_обучения).

### Организационная структура

| Роль | Описание                                                                                                                            |
|------|-------------------------------------------------------------------------------------------------------------------------------------|
| **Заказчик / владелец продукта** | Проект Neolithic — продукт по сбору и аналитике данных для застройщиков                                                             |
| **Основные пользователи** | Аналитики застройщиков, команда Neolithic, дата-инженеры                                                                 |
| **Конечные потребители результата** | Застройщики, которым нужна актуальная картина рынка: сколько квартир в экспозиции, как быстро уходят в сделки, повторные выставления |

### Коммуникация

- Встречи по проекту Neolithic с преподавателями курса MLOps (ИТМО).
- Документирование решений в репозитории и в общих документах проекта.

### Бизнес-цель

**Построить систему матчинга**, которая связывает записи об объектах недвижимости из экспозиции с соответствующими 
сделками и позволяет отслеживать **весь путь объекта**:

```
Экспозиция → исчезновение из экспозиции → сделка → (опционально) повторное появление в экспозиции
```

Это даёт застройщикам и аналитикам:

- понимание, какие объявления реально перешли в продажу;
- метрики скорости продаж и оборачиваемости;
- историю объекта при повторных выставлениях на продажу.

### Существующие решения

| Решение | Ограничения |
|---------|-------------|
| Ручной разбор аналитиками | Не масштабируется, высокая стоимость, субъективность |
| Простые правила (точное совпадение адреса/площади) | Данные в экспозиции и в сделке **различаются** (цена, описание, источник, формат полей); много ложных отрицаний |
| Разрозненные выгрузки без единого идентификатора объекта | Невозможно надёжно строить жизненный цикл и агрегированную аналитику |

**Почему нужен новый подход:** требуется автоматизированный матчинг с учётом неполного совпадения признаков, нескольких 
источников и циклического возврата объектов в экспозицию.

## 1.1 Текущая ситуация (оценка ресурсов)

### Железо и инфраструктура

- Используется существующая инфраструктура Neolithic для хранения и обработки данных.
- Для обучения и инференса модели матчинга — вычислительные ресурсы команды.
- MLOps-конвейер: версионирование данных и моделей, CI/CD, мониторинг качества матчинга.

### Данные

Доступ к данным предоставляется из внутренней PostgreSQL-базы Neolithic. В нём уже есть сделки, справочники корпусов/локаций, 
экспозиция и результаты текущей эвристической сцепки.

| Уровень данных | Таблицы | Что хранится | Объём                                                                     |
|----------------|---------|--------------|---------------------------------------------------------------------------|
| Сырые сделки | `raw.deals` | исходные записи сделок из госисточников: кадастр, номер договора, дата регистрации, описание объекта, площадь, этаж, цена | 902 539 строк                                                             |
| Очищенные сделки | `public.deals` | полный слой нормализованных сделок с признаками объекта и ссылкой на `location_id` | 2 497 359 строк, 598 879 с `location_id`                                  |
| Рабочий срез сделок | `public.deals` с фильтрами `is_primary = true`, `is_residential = true`, `to_delete = false` | целевой сегмент для MVP: первичные жилые не удалённые сделки | 746 292 строки, 402 803 с `location_id`                                   |
| Локации и корпуса | `public.locations`, `public.apartment_buildings`, `public.location_cadastrals` | адреса, `building_id`, `complex_id`, кадастровые номера, признаки корпуса | 6 717 локаций, 6 698 корпусов, 6 387 заполненных первичных жилых корпусов |
| Экспозиция | `exposition.flats` | объявления/квартиры на продаже: источник, `location_id`, площадь, этаж, комнатность, цена, статус активности | 938 725 строк, 236 750 активных с `location_id`                           |
| Текущая сцепка | `exposition.flats_concatenation` | результат rule-based связки сделки с объектом экспозиции | 229 510 строк                                                             |

Исторический диапазон в проверенном срезе: сделки по `registration_date` покрывают период `2016-07-12` — `2026-05-05`, экспозиция по `actualized_at` — `2022-12-31` — `2026-06-05`.

**Источники экспозиции** (объекты на продаже):

- сайты застройщиков;
- ДомКлик;
- Циан;
- Этажи;
- другие площадки по мере подключения.

**Данные по сделкам:**

- государственные ресурсы, данные из которых попадают во внутреннюю базу команды Neolithic;
- сырой слой `raw.deals` и очищенный слой `public.deals`;
- признаки сделки: кадастровый номер, номер и дата договора, дата регистрации, описание объекта, площадь, этаж, номер объекта, 
- цена, продажа по ипотеке, признаки первичного/жилого объекта.

**Особенности данных:**

- между экспозицией и сделкой есть **общие признаки** (ЖК, адрес, площадь, этаж, комнатность, тип объекта и т.д.), но значения могут **отличаться**;
- один физический объект может иметь **несколько записей** в экспозиции (разные площадки, переобъявления);
- после сделки объект может **снова попасть в экспозицию** — нужна поддержка повторных циклов.
- текущая таблица `exposition.flats_concatenation` полезна как baseline и источник псевдоразметки, но не является независимым 
- эталоном качества: часть связок получена правилами, а не ручной проверкой.

**Текущий rule-based baseline в Neolithic:**

- первичная привязка сделки к корпусу через цепочку `raw.deals.cadastral_number → public.location_cadastrals → public.locations → public.apartment_buildings`;
- уточнение корпуса по regex-паттернам номера договора, адресным признакам и `gp`;
- сцепка сделки с квартирой экспозиции каскадом правил: номер квартиры, подъезд и номер на этаже, площадь/этаж/комнатность, площадь/этаж, площадь, совпадение по ЖК;
- в `exposition.flats_concatenation` уже есть 60 731 полное совпадение, 124 092 частичных совпадения и 44 687 записей без совпадений.

**Данные, которые нужно добрать или проверить дополнительно:**

- ручной golden set пар `deal_id → location_id/flat_id` по нескольким регионам, ЖК и застройщикам;
- история появления и исчезновения объявлений, чтобы отличать продажу от снятия с публикации;
- независимые подтверждения по ID ОДС и квартирографии из API ЕИСЖС / наш.дом.рф;
- данные агрегаторов, например ДомКлик: ЖК, корпус, квартира, площадь, этаж, цена, статус, ID корпуса/квартиры из фидов;
- данные сайтов застройщиков, например Брусника: карточки квартир, планировки, дом/корпус, этаж, площадь, цена, статус продажи;
- журнал ручных исправлений и спорных случаев для активного обучения и контроля дрейфа.

Также планируется проверить исследовательский подход с ранжированием кандидатов: для каждой сделки формировать 
набор возможных `location_id`, сравнивать текстовые признаки адреса локации, описания объекта из сделки и номера договора, 
затем выбирать лучшего кандидата только при достаточном отрыве от второго. Конкретную модель и качество нужно фиксировать 
только после проверки на согласованной эталонной выборке.

### Эксперты

- Предметные эксперты Neolithic по рынку новостроек и структуре источников.
- Аналитики для разметки эталонных пар «экспозиция — сделка» и валидации качества матчинга.

### Управление рисками

| Риск | Вероятность / влияние | Митигация |
|------|------------------------|-----------|
| Не уложиться в сроки курса / релиза | Средняя | Поэтапный план, MVP на правилах + ML, приоритизация одного типа объектов (квартиры) |
| Мало или плохое качество размеченных данных для обучения | Высокая | Ручная разметка пилотной выборки, активное обучение, гибрид правил и модели |
| В данных нет устойчивых закономерностей для автоматического матчинга | Средняя | Блокирующие ключи (ЖК + корпус + площадь), fuzzy-matching по адресу, эскалация на ручную проверку |
| Высокий Precision, но низкий Recall (пропуск сделок) | Высокая | Настройка порогов, каскад: строгий матч → мягкий матч → «кандидат» |
| Высокий Recall, но низкий Precision (ложные связки) | Высокая | Двухэтапная верификация, метрики на размеченной выборке, мониторинг в проде |
| Дрейф данных (новые форматы источников) | Средняя | Мониторинг распределений признаков, переобучение по расписанию |

## 1.2 Решаемые задачи с точки зрения аналитики (Data Mining goals)

### Постановка задачи в терминах ML

**Entity resolution / record linkage** — для каждой записи экспозиции (или кластера записей одного объявления) определить:

1. соответствует ли она конкретной сделке;
2. является ли это тем же физическим объектом при повторном появлении в экспозиции.

Формулировки:

- **Бинарная классификация пар** (exposition_record, deal_record) → match / no match.
- **Ранжирование кандидатов** — для каждой экспозиции топ-N сделок с оценкой схожести.
- **Кластеризация / идентификация сущности** — единый `property_id` на весь жизненный цикл объекта.

### Ключевые признаки для матчинга (предварительно)

- идентификаторы и нормализованный адрес (дом, корпус, квартира);
- жилой комплекс, застройщик;
- площадь, этаж, число комнат;
- тип объекта;
- временные окна (дата появления/исчезновения из экспозиции, дата сделки);
- цена (как вспомогательный, не единственный признак).

### Метрики оценки модели

**Основная метрика проекта — Precision@1** на ручной эталонной выборке пар `deal_id → location_id/flat_id`.

`@1` означает, что для каждой сделки оценивается только первый кандидат — та связка, которую система считает лучшей и 
готова принять автоматически. Например, если для одной сделки найдено несколько возможных `location_id`, метрика проверяет, 
оказался ли правильным именно top-1 вариант.

Именно эта метрика выбирается ключевой, потому что ложная сцепка опаснее пропуска: если сделку связать не с тем 
корпусом или квартирой, аналитика застройщика получит неверные сроки продаж, остатки, скорость реализации и историю объекта. 
Если модель не уверена, лучше отправить пару на ручную проверку, чем автоматически записать ошибочную связку.

| Метрика | Роль в проекте |
|---------|----------------|
| **Precision@1** | Главная метрика: доля верных top-1 связок среди автоматически принятых матчей |
| **Recall** | Вспомогательная метрика: доля найденных реальных связок среди всех эталонных связок |
| **F1-score** | Баланс Precision@1 и Recall для сравнения версий модели |
| **Accuracy@k** | Проверка, попадает ли правильная связка в топ-k кандидатов для ручной валидации |
| **Coverage** | Доля сделок/объектов экспозиции, по которым система смогла выдать уверенный автоматический матч |
| **Доля `Полное/Частичное/Нет совпадений`** | Операционная метрика качества текущего rule-based baseline |
| **Доля неоднозначных кандидатов** | Контроль случаев, где первый и второй кандидат слишком близки и нужна ручная проверка |

### Критерии успешности (SMART, уточняются на пилоте)

| Уровень | Precision@1 | Recall | Coverage | Комментарий |
|---------|-------------|--------|----------|-------------|
| Минимально допустимый | ≥ 0.90 | ≥ 0.65 | ≥ 0.50 | MVP: автоматизируем только уверенные случаи, спорные пары уходят на ручную проверку |
| Целевой | ≥ 0.95 | ≥ 0.75 | ≥ 0.65 | Можно использовать в регулярной аналитике с контролем качества |
| Оптимальный | ≥ 0.97 | ≥ 0.85 | ≥ 0.80 | Достижимо после расширения golden set и стабилизации источников данных |

Дополнительно на уровне бизнеса: доля объектов с восстановленным полным жизненным циклом (экспозиция → сделка) не ниже согласованного порога на пилотном ЖК.

### План валидации данных и качества

- выгрузить пилотный срез по нескольким регионам и ЖК из `public.deals`, `public.locations`, `public.apartment_buildings`, `exposition.flats`;
- собрать ручной golden set: минимум 300-500 проверенных связок с балансом полных, частичных, неоднозначных и отсутствующих матчей;
- сравнить новую модель с текущими правилами на одном и том же историческом периоде;
- отдельно считать качество по корпусам, ЖК, источникам экспозиции и типам совпадений;
- проверять не только метрики модели, но и качество входных данных: пропуски `location_id`, площади, этажа, номера 
- квартиры, кадастра, даты регистрации и даты актуализации экспозиции.

## 1.3 План проекта

План охватывает [шесть этапов жизненного цикла ML-модели](https://neerc.ifmo.ru/wiki/index.php?title=Жизненный_цикл_модели_машинного_обучения). Ниже — что будет сделано в рамках проекта по каждому этапу.

### Этап 1. Бизнес-анализ 

- Зафиксированы цель, пользователи, риски, метрики и критерии успеха.
- Согласована постановка задачи матчинга экспозиции и сделок.

### Этап 2. Анализ и подготовка данных

| Подэтап | Действия в проекте                                                                                |
|---------|---------------------------------------------------------------------------------------------------|
| Анализ данных | Инвентаризация `raw.deals`, `public.deals`, `public.locations`, `public.apartment_buildings`, `exposition.flats`, `exposition.flats_concatenation`; профилирование пропусков и неоднозначных кандидатов |
| Сбор данных | Выгрузка пилотного исторического среза из БД Neolithic; подготовка ручного golden set; проверка дополнительных источников: наш.дом.рф, ДомКлик, сайты застройщиков |
| Нормализация | Единая схема полей, нормализация адресов и площадей, дедупликация объявлений внутри экспозиции    |
| Моделирование данных | Сущности: `listing`, `deal`, `property`, `match`, события жизненного цикла                        |
| Конструирование признаков | Кадастровые и адресные признаки, корпус/ЖК, площадь, этаж, комнатность, номер квартиры, временные лаги, источник, текстовая близость описаний |

### Этап 3. Моделирование

| Подэтап | Действия в проекте |
|---------|-------------------|
| Выбор алгоритма | Базлайн: текущие правила Neolithic; ML-гипотезы: классификатор/ранжирование пар, включая проверку текстовой близости адресов и номера договора |
| Планирование тестирования | Train / val / test с временным сплитом; кросс-валидация по ЖК; ручной hold-out golden set |
| Обучение | Итерации подбора признаков и гиперпараметров, логирование экспериментов (MLflow и др.) |
| Оценка результатов | Основная метрика `Precision@1`; дополнительно Recall, F1, Coverage, Accuracy@k, анализ ошибок и сравнение с rule-based baseline |

### Этап 4. Оценка решения

- Сопоставление качества модели с бизнес-целями Neolithic и застройщиков.
- Разбор сильных и слабых сторон пилота, спорных кейсов (повторная экспозиция, переуступки).
- Решение: внедрять текущую версию или доработать данные/модель.

### Этап 5. Внедрение

- Сервис матчинга (batch и/или API) в контуре Neolithic.
- Конвейер: загрузка свежей экспозиции и сделок → инференс → обновление графа жизненного цикла объектов.
- Интеграция с дашбордами и отчётами для застройщиков.
- CI/CD, контейнеризация, версионирование моделей.

### Этап 6. Тестирование и мониторинг

| Тип | Действия |
|-----|----------|
| Дифференциальные тесты | Сравнение новой версии модели со стабильной на фиксированном тестовом срезе |
| Контрольные тесты | Время инференса и обучения, регрессии по SLA |
| Нагрузочные тесты | Пиковые объёмы объявлений по крупным ЖК |
| Мониторинг в проде | Precision@1 на shadow-разметке, Coverage, доля ручных проверок, распределение скоров, дрейф признаков, алерты по пропускам ключевых полей |
